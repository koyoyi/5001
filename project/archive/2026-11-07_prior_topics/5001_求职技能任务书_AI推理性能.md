## 1. 直接推荐这个题

**中文：统计学习能否指导 LLM 推理服务的并发配置选择？**

**English: Can Statistical Learning Guide Concurrency Selection for LLM Serving?**

做一个本地 LLM 推理服务，自己采集不同输入长度、请求强度与服务并发配置下的性能数据。再用 Ridge、随机森林等模型预测延迟，推荐候选配置，并通过独立实验复测推荐是否有效。

研究重点是服务性能和配置决策。预训练语言模型是被测系统，5001 中训练的是性能预测模型。这能自然连接 AI 基础设施、后端服务、性能工程与 MLOps，也涉及 IDC 的计算服务层。

## 2. 为什么可以在当前电脑上起步

只读检查确认：

- CPU：Intel i7-11800H，8 核／16 线程。
- 内存：约 32 GB。
- GPU：RTX 3060 Laptop，6 GB 显存。

这些硬件适合先试小模型，尚不能证明特定后端、上下文或并发配置已经可运行。第一阶段只做兼容性和测量小试。

建议采用一个小模型和一个后端：

- 模型候选：[Qwen 官方 Qwen3-0.6B-GGUF](https://huggingface.co/Qwen/Qwen3-0.6B-GGUF)。
- 后端候选：[llama.cpp server](https://github.com/ggml-org/llama.cpp/tree/master/tools/server)，优先核实 Windows 原生构建的 GPU 支持。

llama.cpp 的服务端提供并行 slots、连续批处理和指标接口；具体可用参数以最终固定版本的帮助信息和启动日志为准。[官方服务文档](https://github.com/ggml-org/llama.cpp/tree/master/tools/server)

**slots 是服务可处理的并行序列槽位，不是固定请求批大小。** 也不要把后端的 token batch 参数当成同时到达的请求数。实验中分别记录服务 slots、客户端到达率、实际在途请求及上下文限制。

先固定模型文件、精度、生成策略、缓存策略与每请求上下文限制。暂不同时比较多模型、量化方案和多种后端。

改变 slots 后要检查后端实际报告的每槽上下文容量，避免把总上下文的重新分配误认为纯并发效应。缓存关闭或重置方式也须实测确认，不能只假定每次重发相同 prompt 都在执行同样的计算。

## 3. 三个可以被实验否定的问题

1. **性能预测**：在未见的工作负载—配置组合上，Ridge 或 RF 能否比训练集常数／按配置均值更准确地预测首 token 延迟？
2. **系统机制**：并发 slots、输入长度与请求到达率的交互，能否解释吞吐增加时尾延迟的变化？
3. **决策价值**：模型推荐是否比预先固定的配置获得更多按时成功请求？它距离候选集合中的实测最好配置有多远？

允许结论为“简单配置已经足够”或“模型预测误差不足以支持可靠推荐”。不能预设 RF 必胜，也不能只报告速度柱状图。

## 4. 先把测量协议做对

### 4.1 最小实验范围

先试 slots 为 1、2、4，以及短、中、长三类输入。输出 token 预算固定在一个较小值，实际生成长度仍须记录。请求强度先以四个试验等级覆盖轻载到接近饱和，具体数值由独立小试确定并在正式采集前冻结。

起步设计约为 3 个 slots × 3 类输入 × 4 个到达率，形成 36 个组合；每个组合至少三个独立运行批次。它是采集计划，实际耗时、有效请求数和稳定性须经小试调整。

训练数据来自自己重复运行的服务实验。**一个 run 是一个组合的一次完整运行；其中多条请求不等于多个独立运行。**

### 4.2 流量与时间

- 主实验采用开放到达：请求按预定到达计划产生，不能等上一条返回后才发下一条，再声称测得固定到达率下的排队性能。
- 同时记录计划到达、实际发送、首个有效内容、最后内容及结束时间；记录客户端调度延迟。
- 计时采用单调时钟。报告从发送开始的 TTFT，同时检查从计划到达开始的用户等待，防止压测客户端落后却被隐去。
- TTFT 是首个有效生成内容到达的时间差；空事件、角色事件和心跳不计为首 token。流式事件不必一一对应 tokenizer token，不能把事件数直接当生成 token 数。
- 预热不计入正式测量。固定供电模式、主要后台负载和缓存策略，随机化各配置的执行顺序，并跨批次重复。
- 退出、超时、连接失败和 OOM 全部进入日志；不能只保留成功请求。

MLPerf 与 vLLM 都区分不同负载场景及在线／离线测量。本项目可参考这些测量概念，但不声称是符合官方规则的 MLPerf 成绩。[MLPerf 规则](https://github.com/mlcommons/inference_policies/blob/master/inference_rules.adoc)、[vLLM 基准工具](https://docs.vllm.ai/en/latest/api/vllm/benchmarks/index.html)

### 4.3 不把测量指标混用

| 指标 | 定义及用途 |
|---|---|
| TTFT | 从实际发送到首个有效内容；衡量开始响应的等待 |
| 计划到达至首内容 | 补充检查客户端延迟和完整等待 |
| E2E latency | 从发送到完成；包含生成过程 |
| Offered rate | 计划产生的请求数／产生流量的时长 |
| Completed throughput | 成功完成请求数／预先说明的统计时长 |
| Goodput | 成功完成且满足已冻结延迟目标的请求数／统计时长 |
| 失败／拒绝比例 | 失败、超时、拒绝分别统计；分母为全部发起请求 |

停止发流量后的排空时间与未完成请求必须单列；吞吐和 goodput 使用同一套明确的计时边界。推荐配置不能靠拒绝大量请求让成功子集的 p95 变漂亮。

初步以 p95 TTFT 为主要运行级延迟目标，补充 E2E、goodput 和失败率。每个 run 要有足够请求支撑 p95；小试若发现尾部分位不稳定，应增加样本或改为更稳健的主指标，不能用少数请求包装稳定的 p99。

## 5. 5001 的统计学习设计

### 输入与标签

可用输入：配置、输入 token 分布、请求输出预算、计划到达率及事先定义的负载类型。真实输出长度、实测 GPU 使用率、实测完成吞吐和实测排队长度属于本轮运行结果，不能直接作为运行前配置推荐模型的输入。

主标签：每个 run 的 p95 TTFT；必要时在训练中使用对数变换。同时拟合运行级 goodput，用于配置选择。输入和标签单位、变换及聚合方式写入数据字典。

### 模型阶梯

1. 训练集常数／按配置均值基线。
2. Ridge：输入长度、slots、到达率，配合少量有系统含义的交互。
3. 随机森林：检验非线性及饱和区域的增益，限制复杂度和调参预算。
4. 若仍有时间，再补样条／GAM；不把添加更多模型作为成果数量。

只有约百次独立 run 时，数据规模仍然有限。避免把上万条同一 run 请求当作上万次独立系统实验来支撑复杂模型。

### 验证与决策评估

- 同一个 workload—configuration 组合的重复 run 全部放在同一分组；不得随机拆进训练和测试。
- 训练阶段按完整组合做分组交叉验证；预留一批组合，专门测试未测组合上的泛化。
- 另在后续独立 session 复测一组已冻结工作负载，比较预先固定配置、模型推荐配置及候选配置实测结果。
- 推荐器只能看到训练数据与当前已知工作负载描述；用于定义“实测最好”的测试结果只在推荐冻结后揭示。
- 回归报告 MAE／RMSE及按负载分组误差；推荐报告延迟目标违反率、goodput 和相对实测最好配置的差距。
- 训练、调参、推荐选择与最终对比使用分开的数据角色。置信区间按 run／session 处理，不能把相关请求独立重采样。

延迟目标及允许的失败／拒绝比例要在正式测试前给定，并说明这是课程实验设定。某种工作负载下若没有候选配置满足要求，推荐器应返回“无可行配置”，不能强行给答案。

推荐时，对候选 slots 分别预测 p95 和 goodput，在预测延迟达标且落在训练数据有效覆盖范围的候选中，选预测 goodput 较高者。失败／拒绝约束最终通过独立复测检验，不能因预测延迟达标就声称已经保证 SLO。测试结果揭示后不再回头更换推荐配置。

## 7. 更偏底层 GPU 的备选

**题目：有限试跑能否帮助找到接近最优的 GPU 矩阵乘法内核配置？**

使用 [UCI SGEMM GPU kernel performance](https://archive.ics.uci.edu/dataset/440/sgemm+gpu+kernel+performance)：241,600 组可行配置、14 个配置参数、每组四次计时，CSV 约 13.7 MB。它是已有 GPU OpenCL 矩阵乘法实验数据，适合研究有限采样预算下的性能建模和配置筛选。

可比较随机采样、Ridge、RF 的筛选效果，绘制采样预算与所选配置实际性能之间的关系。四次计时作为重复测量处理，不互相充当输入，也不跨训练／测试拆分。

这个方案更容易按时完成。若要补实际编程，可以实现并验证一个小型分块矩阵乘法示例，再分析分块、访存与并行的关系；示例的性能和旧数据不能混为一套实验结果。公开数据仅涉及旧单卡和固定矩阵尺寸，不支持跨 GPU 或现代 LLM 的性能结论。

## 8. 简短英文 Proposal 初稿

**Title:** Can Statistical Learning Guide Concurrency Selection for LLM Serving?

**Background and motivation.** LLM services must balance response latency, throughput and failed requests. We will study whether a statistical performance model can guide configuration selection on a single local machine. The intended contribution is a reproducible experiment and an independently tested configuration decision.

**Research questions.** Can Ridge regression or a random forest predict latency for previously unmeasured workload–configuration combinations? Which workload interactions account for performance degradation? Does model-guided selection improve timely successful completions over a fixed configuration?

**Data.** We will collect controlled experiments using one small pretrained language model and one pinned inference backend. Configuration, prompt-length profile and offered request rate will vary, while model precision and generation policy remain fixed. A run, rather than an individual request, will form the primary performance observation. Exact run and request counts will be frozen after a compatibility and measurement pilot.

**Methods.** We will compare training-mean baselines, Ridge with limited interactions and a random forest. The primary regression response will be run-level p95 time to first content. A decision stage will select among configurations subject to predeclared latency and failure constraints.

**Validation.** Repeated runs of the same workload–configuration combination will remain grouped. Training-only grouped validation will tune models, with combinations reserved for final testing. Recommendations will then be evaluated in a later independent session. We will report prediction error, constraint violations, goodput and the gap to the measured best candidate. Failures and rejected requests will remain visible.

**Contribution and limitations.** Deliverables include an asynchronous load generator, SQL experiment records, a reproducible performance model and configuration evaluation. Results concern one model, backend and consumer GPU. They will not establish production capacity or cross-hardware generalisation.

**Timeline.** Complete the pilot first, then collect experiments and fit baselines, followed by nonlinear comparisons and independent validation. Freeze results before preparing the recording and submission.

Team, members, UIDs and responsibilities remain to be supplied.
